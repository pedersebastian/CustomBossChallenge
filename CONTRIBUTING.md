# Contributing

Technical notes for building and testing Custom Boss Challenge. For what the mod does and how to install it, see the
[README](https://github.com/pedersebastian/CustomBossChallenge/blob/master/README.md).

## Building from source

1. Install the .NET SDK, MelonLoader and BTD6 Mod Helper (with the game run at least once so Mod Helper can set up
   its references), and [Node.js](https://nodejs.org/) 24: the build makes the copy of the past boss events the mod
   carries with it, and a Release build fails without Node (see [Boss events archive](#boss-events-archive)).
2. Clone this repository into your BTD6 mod sources folder.
3. Build `CustomBossChallenge.sln` (for example `dotnet build -c Release`). The built DLL is copied to the game's
   `Mods` folder automatically.

`Icon.png` is generated by `tools/GenerateIcon.ps1`
(`powershell -ExecutionPolicy Bypass -File tools/GenerateIcon.ps1`).

### The tier glow shader

Tiers above 5 glow with a shader of the mod's own, `UnityProject/Assets/TierGlow/TierGlow.shader`. The game can only
load shaders built with its own Unity version, so it is built into `Bundles/tierlook.bundle`, which is committed and
built into the DLL; the checks on GitHub don't build it, since that needs a Unity license. Only rebuild it after
changing the shader, or when a BTD6 update moves to another Unity version (MelonLoader logs it as `Unity Version`, and
the game's URP version is in `BloonsTD6_Data/resources.assets`, e.g. `render-pipelines.universal@17.3.0`):

1. Install that Unity version (the same major and minor version, e.g. 6000.3, with the latest patch is enough) with
   Unity Hub and activate a Personal license. No modules are needed.
2. Build the bundle:

   ```
   "C:\Program Files\Unity\Hub\Editor\<version>\Editor\Unity.exe" -batchmode -quit -nographics -projectPath UnityProject -executeMethod BuildTierLook.Build -logFile -
   ```

   It compiles the shader for Direct3D 11, Direct3D 12 and Vulkan and writes `Bundles/tierlook.bundle`.
3. Run `TierLookTest` (`CBC_TESTS=TierLookTest`): it fails if the game can't use the shader. Without the bundle, or
   when the game can't run it, players still get a simpler glow made from the game's own shaders.

The look itself (colours per boss, strength per tier) is in `Config/TierLook.cs`. `TierLookTour` saves tiers 5-10 of
every boss next to each other when the game is started with `CBC_SCREENSHOTS=<folder>` (`CBC_TIERLOOK_BOSSES=Lych,Vortex`
picks bosses).

### The mystery map effects

The haze and dice a secret Random boss shows on the map (#285) are modelled in Blender. The game can't load a model
from an asset bundle, so `tools/blender/export-mystery.py` writes the meshes to `Bundles/mystery-fx.mesh.gz` (format in
the script; the toon shading is baked into UVs on a ramp the mod makes), which is committed and built into the DLL, and
the mod animates them (`Visuals/MysteryMapFx.cs`). After changing `tools/blender/mystery-fx.py`, rebuild it:

```
"C:\Program Files\Blender Foundation\Blender <version>\blender.exe" --background --factory-startup --python tools/blender/build-mystery.py
```

or, in an open Blender with its MCP add-on, `python tools/blender/run-in-blender.py tools/blender/mystery-fx.py` and then
`export-mystery.py`. The headless build also saves `tools/blender/mystery-fx.blend`. `MysteryMeshDataTests` checks the
file, `MysteryMapFxTest` the effects in the game.

## Running the tests

### Unit tests

The logic that doesn't need the game (tier, spawn round and skull math, the Max Paragons slider, Random's chances and
weights and the names it gives a setup, the keyboard shortcut rules, the share code format, and the formats of the
mod's files) has xUnit tests in `UnitTests/`. Those source files are built on their own in
`Shared/`, so the tests build and run in seconds without BTD6:

```
dotnet test --project UnitTests
```

Keep the files in `Shared/` free of the game's types (`Il2Cpp...`, `BTD_Mod_Helper`), or the project won't build. A
class with only a little that needs the game is split in two `partial` files, the part without the game in `Shared/`:
`ChallengeLimits.Options.cs`, `ParagonMath.Slider.cs` and `BossRandomizer.Weights.cs`.
The one exception is `Shared/BossType.cs`, a stand-in for the game's `BossType` so that `BossOptions` builds there.
`BossTypeTests` checks it against `web/src/data/game.json`, so when the game adds a boss, update `game.json` first and
then the stand-in.

**Save files.** `SaveFormatTests` reads `Continue.json`, `LastSetup.json` and `SavedSetups.json` from every released
file version, from `UnitTests/Fixtures/saves/`. They are read through `ContinueFormat`, `LastSetupFormat` and
`SavedSetupsFormat`, which don't need the game. When you raise a file's `Version`, first add a fixture of the old
version to that folder, written by the released mod. The test fails when a version has no fixture. A file from a newer
version of the mod is never read, overwritten or moved.

### Property tests

Share codes are also tested with random data, in F# with [FsCheck](https://fscheck.github.io/FsCheck/), in
`PropertyTests/`. Thousands of random setups the Boss Creator can make, and broken codes, check that:

- a code reads back as exactly the setup it was made from, and encoding that setup again gives the same code;
- codes use the oldest version that holds the setup (`CBC1:` to `CBC7:`), and only characters chat apps leave
  alone;
- broken codes (cut short, changed, junk, too big once unpacked) are refused as `Invalid` or `TooNew` and never throw;
- a hand made challenge only keeps the fields `CodeFormat.ChallengeFields` allows, with their types, and nothing the
  Boss Creator makes is ever left out.

`TextProperties.fs` does the same for what players type and paste: a tier's own speed and health stay in range for any
int, near its limits too (#168); bosses per tier and custom skulls read back the same once shown; custom skulls are at
most ten, falling, from 1 to 99 %; and a code is found inside the text around it, while finding it never throws (#187).

**What a code may set.** `CodeFormat.ChallengeFields` lists the challenge fields a code may set: the settings of the
game's Challenge Editor and the Boss Creator, each with its JSON type. Everything else in a code is ignored and named in
the log, so a code can't set what no player can (#108). When the game's Challenge Editor gets a new setting, add it
there, give it a range in `ChallengeLimits.Sanitize`, and run `WebDataTest` so the website gets the same list.
`MaliciousCodeTest` checks in-game that the examples and Random only use fields on the list.

```
dotnet test --project PropertyTests
```

The tests run `Persistence/CodeFormat.cs` (the text format, without the game), against the defaults in
`web/src/data/game.json`. When a property fails, FsCheck shrinks it to the few values that matter and prints them as
the JSON the code holds; add that case to `SetupCodeTest` or `WebDataTest`'s fixtures, then fix it.

They also check `web/test/generated-codes.json`: 200 random codes and 50 or so broken ones from a fixed seed, which
the website's tests must read exactly like the mod. After changing the generators or the code format, write it again:

```
$env:CBC_GENERATED_CODES = "1"; dotnet test --project PropertyTests; Remove-Item env:CBC_GENERATED_CODES
```

### Mutation tests

Mutation tests find code the tests run but don't really check (#268). [Stryker](https://stryker-mutator.io/) makes
many small changes to the code, one at a time (a *mutant*: `<` to `<=`, `+` to `-`, a condition to `true`, a string to
`""`), and runs the tests on each. A mutant no test fails on has *survived*: that change could ship without a test
noticing. They are slow, so they aren't part of the checks on every push; run them after changing the math or the code
format, or look at the weekly report.

- **Website** (StrykerJS): the share-code package (`web/packages/share-code/src/`) and the preview math
  (`web/src/preview/`), checked by all of `npm test`. Settings in `web/stryker.config.mjs`. In `web/`:

  ```
  npm run mutation
  ```

  The report is `web/reports/mutation/index.html`. To try one file:
  `npm run mutation -- --mutate src/preview/timeline.ts`. `scripts/mutation.mjs` first copies `CHANGELOG.md`,
  `Localization/` and `data/` into `web/.stryker-tmp/`, since Stryker runs the tests in a copy of `web/` there and
  some tests read those files. The tests run with `vitest.stryker.config.mjs`, which points `@cbc/share-code` at that
  copy: `node_modules` links to the real package, which Stryker never changes. Mutants in code that runs once when a module loads
  (`ignoreStatic`) are left out: each would run every test, which more than doubles the time. So don't load modules
  again in a test (`vi.resetModules()` and `await import(...)`): Stryker then counts that test as covering all the code
  that runs when those modules load, and tries those mutants against it alone, so hundreds survive. To swap a global a
  module uses as it loads, stub it in `vi.hoisted` instead (see `web/test/skull-labels.test.ts`).
- **Mod math** (Stryker.NET): the pure math in `Config/` (`TierMath`, `TierBossMath`, `SkullMath`, `RankedTime`,
  `ParagonMath.Slider`, `HealthSteps`, `BossRoundsMath`, `BossRowMath`, `DifficultyRating`, `ShownNumber`), built from
  `Shared/` and checked by `UnitTests` and `PropertyTests`. No game needed. Settings and the file list in
  `Shared/stryker-config.json`, the tool's version in `Shared/.config/dotnet-tools.json`. In `Shared/`:

  ```
  dotnet tool restore
  dotnet stryker
  ```

  The report is in `Shared/StrykerOutput/<time>/reports/mutation-report.html`. To try one file, add
  `--mutate ../Config/SkullMath.cs`. Stryker.NET also compiles mutants of the other files in `Shared/` and prints
  compile warnings for some of them; only the listed files are tested and counted. Mutants of `static readonly` fields (like
  `TierBoss.Bosses` or a `Regex`) survive in some runs and not in others, since the field is set once per test process;
  the score can move by a few percent from that alone. `"coverage-analysis": "all"` would fix it, but runs every test
  for every mutant, which takes hours.

A mutant that makes the tests run too long counts as a *Timeout*, which Stryker scores as killed: usually the change
made a loop that never ends. On a busy machine (two Stryker runs at once, a build, a video call) a mutant the tests
don't catch can time out too, so a local Timeout isn't proof that a test catches it (#302). Stryker itself starts a test
runner on every core but one, which can be enough: run it with nothing else heavy going on, try fewer runners
(`npm run mutation -- --concurrency 4`), and trust the weekly run on GitHub when the two disagree. `timeoutMS` in
`web/stryker.config.mjs` gives every mutant 15 s more than its tests took without it.

`.github/workflows/mutation.yml` runs both every Sunday and by hand (Actions → Mutation tests → Run workflow), and
uploads each HTML report as an artifact. It never fails on a low score. When a survivor matters, add a test that fails
on it; when it doesn't (an equivalent mutant, a log text, a guard that can't be reached), leave it, or file an issue
if it needs a closer look.

### In-game tests

Everything else runs inside the game, with automated tests built on Mod Helper's `ModTest`. They cover:

- preparing the editor's challenge for a boss game
- the Random button: a thousand random setups that must all be playable, spread like the game's own randomizer
- extra tier models for every boss and Elite tier, Speed and Health per Tier for every tier of every boss, and real
  games played to victory with 6 and with 2 tiers
- a vanilla and a custom Bloonarius game compared side by side (speed, health, skulls, cash, unranked)
- the ranked and co-op guards, and that every record, boss progress and badge method is still guarded after a
  game update
- restarting a custom game, and losing one to a boss that isn't defeated
- the Max Paragons limit, enforced by the game in a custom game with a real paragon placed
- saving and loading the last setup, including broken files and values out of range
- share codes: the round trip, short codes, and broken, damaged or too new codes that must never load
- hand made, malicious codes: type names, extreme values, rich text in the name, and codes that unpack to too much
  or nest too deeply
- the main menu button, and the whole Boss Creator flow in the real Challenge Editor, from editing the boss options
  to copying and pasting share codes and pressing Play, including that the normal Challenge Editor and your own
  draft stay untouched and that Play refuses unsupported modes and missing bosses
- the keyboard (`KeyboardTest`): the Ctrl shortcuts, Tab, the arrows, Enter, Space and Delete through the Boss
  section's controls (`BossEditorSection.FocusStops`, which controller support can use too: each stop knows how to
  step, press and reset its control), Ctrl+Z and Ctrl+Y (`BossHistory`), Esc in a field cancelling only the
  edit, and nothing of it in the normal Challenge Editor. Real key presses can't be faked, so the test hands the key
  press to `BossCreatorKeys.Handle`
- the layout on 16:9, 16:10, 4:3, 21:9 and 32:9 (`LayoutTest`): the Boss Creator button and Play overlap nothing,
  stay on the screen, Play stays behind the editor's own panels, and every control of the Boss section stays inside
  it. The game can change its resolution even with `-batchmode`, so this runs with the other tests

Run them from Visual Studio / Rider with the **BloonsTD6 (Tests)** launch profile, or from the game folder:

```
BloonsTD6.exe moddingDev -batchmode --modhelper.offline --modhelper.only='CustomBossChallenge;' --modhelper.noaudio --modhelper.run -q test mod CustomBossChallenge
```

The result is written to `MelonLoader/Latest.log`, e.g. `Ran 25 test(s), 25 succeeded, 0 failed`. Each test logs
`starting` and `done in Ns`, so the log shows which tests take the time.

#### Which tests to run

The in-game tests come in two suites (#246):

- **Quick suite**, about 8 minutes: start the game with `CBC_SUITE=quick`. It runs every test except the slow ones
  marked `[FullSuiteOnly("...")]`, which play long games, every boss, every language or measure memory. It includes the
  core: the Boss Creator (`BossCreatorTest`), a custom game with a retry (`RetryTest`), Continue (`ContinueTest`),
  the Rules panel, the layout, the keyboard, share codes and saved setups. Add the slow tests of the area you changed
  with `CBC_TESTS`, e.g. `CBC_SUITE=quick` and `CBC_TESTS=TierLookTest,TierLookLifecycleTest` for the tier look.
- **Full suite**, about 38 minutes: start the game without `CBC_SUITE` and `CBC_TESTS`. Only its receipt counts
  for a release.
- `CBC_TESTS` alone runs only the tests it names, e.g. while working on them.

#### Tests in every language

The tests must pass whatever language the game is in (#291). `CBC_LANGUAGE=Arabic` (any language the game has, or
`Monkey` for its joke Monkey Cipher) runs every test in that language: `Tests/TestLanguage.cs` switches the game to
it before each test and puts the player's own back after it. `.github/scripts/Run-InGameTests.ps1` runs the tests in
several languages one after the other and prints a table of what failed, e.g.
`-Language Arabic -Suite full`, or `-Language All` for the quick suite in every language (about 3 hours).

- **Compare what the game shows with the mod's texts, through `Tests/ScreenText.cs`**: `text.Shown()` against
  `ScreenText.Plain(Texts.X.T())`, or `text.Shows(part)`. Never compare `TMP_Text.text` directly, and never with
  English written into the test. The game keeps a right-to-left text reversed, so in Arabic `40` is `04` in `.text`,
  and the mod leaves the tags out of popups and lists there (`LanguageText.ForGameText`). `Shown()` turns it back and
  leaves the tags out. A mod text that the game or Mod Helper looks up by its key (a modifier's `titleLocKey`, Mod
  Settings and their info popups) shows the same as `Texts.X.T()`: the mod puts its Arabic into the game's table
  shaped (`LanguageText.ShapeTable`, #292). For a text as it is written, use `LanguageText.WrittenText(key)`, never
  `Localize(key)`.
- Don't count on how long a translation is: a text that wraps or shrinks in English may fit on one line in another
  language.
- Run the quick suite in Arabic after changing a text a test looks at, and before a release. Run all languages now
  and then.
- The receipt says which language the run was in (`language`). A full run counts for a release in any language.

A new test is in the quick suite. If it takes more than about 20 seconds, mark it `[FullSuiteOnly]`, with the reason,
so the quick suite stays under 15 minutes. `Tests/TestSuite.cs` has the rules.

What a change needs before its PR:

| Change | In-game tests |
|---|---|
| C# (the mod or its tests) | The quick suite, plus the slow tests of the area that changed |
| `Localization/*.json` | `Check-Localization.ps1` (see Translations); the quick suite if a text got longer, and `LanguageLayoutTest` |
| Only `web/`, `docs/`, `tools/`, `UnitTests/`, `PropertyTests/` or `.github/` | None: their own tests run on GitHub |
| A release | The full suite, with its receipt committed (below) |

- **A failure is fixed, then the whole suite runs again**, not only the test that failed: a fix can break another test.
- **The full suite also runs between releases**, about after every third merged C# PR, so a failure only has a few PRs
  to come from. If it fails, go through the PRs merged since the last green full run to find which one broke it.

On a Debug build, a run of every test also writes `TestResults/ingame.json` in the repo when the game quits
(`TestRunReport`): the mod and game version, the commit, which tests failed or were skipped, and `sourceHash`, a
fingerprint of the mod's own code from `.github/scripts/Get-SourceHash.ps1`. It covers every file that ends up in the
DLL or the Thunderstore package: the `.cs` and `.csproj` files (`Tests/` included, since the tests are built into the
DLL), `Localization/*.json`, the `.json` files in `Config/` (the CHIMPS round sets), every other file the `.csproj`
builds in as an `EmbeddedResource` by name, `Bundles/*.bundle`, the `.png` files, `README.md` and `thunderstore.toml`,
plus `global.json`. It leaves out `CHANGELOG.md` and `LICENSE` (the release rotates the CHANGELOG after the tests ran), and
`UnitTests/`, `PropertyTests/`, `web/`, `docs/`, `tools/` and `.github/`, so changing only those doesn't need a new
run. A test is skipped when it passes without
checking what it normally checks (`Skip`), e.g. tests left out by `CBC_SUITE=quick` or `CBC_TESTS`, or `WebDataTest`
writing its files. `suite` says which kind of run it was: `full`, `quick` or `selected`; a release needs `full`.
`ContinueAfterCrashTest` needs two starts of the game (`CBC_CRASH_PHASE`, `CBC_CRASH_FOLDER`), so a normal run lists it
under `onRequest` instead: not passed, but not keeping the run from counting for a release.

Tests never touch the player's own files: `CustomBossTest` gives every test temporary stores for the unfinished
game, the last setup and the saved setups, and puts the player's back afterwards.

Some failures can't be made to happen on purpose, so the mod has test hooks for them: `CustomBossChallenge.FailNextUpdate`
(a frame update that throws) and `CustomBossRetries.FailNextSnapshot` (a round whose map save can't be written). They
are internal, only tests set them, and `CustomBossTest` resets them before every test.
A release needs this report (see **Release version** below), so before tagging:

1. Bump `Version` (and `WorksOnVersion`) in `ModHelperData.cs`.
2. Build Debug (`dotnet build -c Debug`) and run the full suite of in-game tests (without `CBC_SUITE` and
   `CBC_TESTS`).
3. Commit `TestResults/ingame.json` with the version bump.
4. Make the README's pictures again (below), look through the ones that changed, and commit them with
   `TestResults/screenshots.json`.
5. Run `Check-Release.ps1` (below), then tag. It warns when the pictures weren't made for this version.

#### README pictures

The pictures in the README (`docs/*.jpg`) come from the game, in one command (#269). It is a step before a release
only, not for every change:

```
powershell -ExecutionPolicy Bypass -File tools/screenshots/Make-Screenshots.ps1
```

It needs the game closed and a Debug build in its `Mods` folder. It starts the game windowed with only this mod, runs
`ScreenshotTour` and `TierLookTour` (a few minutes; leave the window alone), and makes every picture listed in
`tools/screenshots/pictures.json` from their screenshots: scaled to 1280x720, cropped, or for `tier-look.jpg` a grid
of tiers 5-10. The tour is always in English, at the size in `pictures.json` (1920x1080, so crops stay sharp), with
fixed setups and names, and it doesn't touch the player's setups. Animations make every run a little different, so a
picture only replaces the one in `docs/` when more of its pixels changed than its `tolerance` (1% unless
`pictures.json` says otherwise); the table at the end says which ones changed, and git shows only those. Look at
each changed picture before committing it. The script writes `TestResults/screenshots.json` with the mod's version,
which `Check-Release.ps1` looks at to remind you when a release's pictures weren't made.
`-SkipGame` makes the pictures again from the last run's screenshots (e.g. after changing a crop), `-Force` replaces
all of them. A new picture in the README needs a capture in the tour and a line in `pictures.json`;
`node --test "tools/screenshots/*.test.mjs"` (also run on GitHub) checks that the two lists match.

`ScreenshotTour` only runs in a windowed game (without `-batchmode`) started with the environment variable
`CBC_SCREENSHOTS=<folder>`. To look at other screen formats, also set `CBC_RESOLUTIONS`, e.g.
`1280x800,1024x768,1680x720,1920x540`: the tour is then taken once per size, each in a subfolder of `<folder>` named
after the size.

### Compatibility with other mods

Players run this mod next to others, so it is tested with the most downloaded mods and the ones that touch bosses,
the Challenge Editor, rounds, the main menu or saves (listed in `.github/scripts/compat-candidates.json`). The results
are in [issue #24](https://github.com/pedersebastian/CustomBossChallenge/issues/24). Run this again after a BTD6 update
or when a mod in the list changes a lot. The other mods are third-party code: they are downloaded into a folder outside the repo and only run
inside the game.

```
# 1. Download the latest release of every listed mod (prints name, size and SHA-256)
powershell -ExecutionPolicy Bypass -File .github/scripts/Get-CompatMods.ps1 -Out C:\cbc-compat\mods

# 2. Which methods both mods patch, without the game
dotnet fsi .github/scripts/Scan-Patches.fsx "<game>\Mods\CustomBossChallenge.dll" C:\cbc-compat\mods C:\cbc-compat\scan.md

# 3. All in-game tests with this mod alone, then with each other mod (A, B, all, a name, or names joined by +)
powershell -ExecutionPolicy Bypass -File .github/scripts/Test-ModCompatibility.ps1 -ModsFolder C:\cbc-compat\mods -Results C:\cbc-compat\runs -Mods none,A,B

# 4. Screenshots with each mod, compared with two runs of this mod alone (the second one measures animation noise)
powershell -ExecutionPolicy Bypass -File .github/scripts/Test-ModCompatibility.ps1 -ModsFolder C:\cbc-compat\mods -Results C:\cbc-compat\runs -Mods none,none -Screenshots
powershell -ExecutionPolicy Bypass -File .github/scripts/Compare-Screenshots.ps1 -Baseline C:\cbc-compat\runs\screenshots\none -Candidates <second baseline>,<mod folders> -FirstIsNoise -Out C:\cbc-compat\report
```

`Test-ModCompatibility.ps1` copies each mod into the game's `Mods` folder for one run and removes it afterwards,
stops if the folder isn't as it was, copies the game profile to `<Results>\profile-backup` before the first run, and
reruns failing tests once so that a flaky test isn't blamed on another mod. Each run adds a line to
`<Results>\results.jsonl`, and its `Latest.log` is kept in `<Results>\logs`.

`ModConflictTest` writes every other mod's patch on a method this mod patches to the log as a `CBC-CONFLICT|` line.
`HarmonyBehaviourTest` checks what another mod's prefix can do to ours: in MelonLoader's Harmony every prefix and
postfix still runs when one of them skips the method, so another mod can't switch a guard off that way, only change a
value before or after us. Outside of tests, the mod logs a warning at startup when another mod patches one of the
guards (`[GuardPatch]`), so a bug report's `Latest.log` shows it.

## Checks on GitHub

`.github/workflows/checks.yml` runs on every push to a branch and every pull request, without the game:

- **Translations**: every `Localization/*.json` must be valid JSON without duplicate keys, have exactly the keys of
  `English.json` in the same order, keep its `{0}` placeholders and leave no text empty, and every text in
  `Menus/Texts.cs` must exist in English. Every translation must be made from the English text as it is now, as
  recorded in `Localization/english-sources.txt` (see Translations below).
- **Release version** (releases only): the tag must match `Version` in `ModHelperData.cs`, which Mod Helper uses to tell
  players about updates, and `CHANGELOG.md` must have notes for it. `TestResults/ingame.json` must show a full
  suite run (not `CBC_SUITE=quick`) on that version, with none failed or skipped, and its `sourceHash` must match the tagged code,
  so changing the mod's code after the tests ran means running them again. Run it before tagging.
- **Unit tests**: `dotnet test --project UnitTests`, see above. The in-game tests can't run on GitHub and still have
  to be run locally; the release check only sees their report.
- **Property tests**: `dotnet test --project PropertyTests`, see above.
- **Website**: `npm test` and `npm run build` in `web/`, see below.
- **Mutation tests** are not here: `mutation.yml` runs them weekly and by hand, see above.
- **Boss events**: `node --test "tools/boss-events/*.test.mjs"`, the tests of the boss events backfill and archiver,
  see below.
- **Game version**: `node --test "tools/game-version/*.test.mjs"`, the tests of the daily check for a new BTD6 version,
  see [Updating for a new BTD6 version](#updating-for-a-new-btd6-version).

The first two are PowerShell scripts that also run locally in Windows PowerShell:

```
powershell -ExecutionPolicy Bypass -File .github/scripts/Check-Localization.ps1
powershell -ExecutionPolicy Bypass -File .github/scripts/Check-Release.ps1 -Tag 2.3.0
```

`.github/workflows/build.yml` builds the mod itself, against the game's assemblies, on every push and every pull
request, so a change that breaks the mod build fails before it is merged. Only a tag (or a run by hand with a `tag`)
publishes anything.

### Releases

`.github/workflows/build.yml` builds the mod on every push. For a release (a tag like `2.10.0`, or running the
workflow by hand with a `tag`) it first runs all of `checks.yml`, the **Release version** check included, and only
when every check passes does it build the DLL, publish it to Thunderstore and create the GitHub release. A tag whose
checks fail releases nothing: fix the problem, delete the tag and push it again.

**Players read the changelog** (#264). The mod is built with `CHANGELOG.md` inside it, and after an update the Boss
Creator shows the new version's `### Added` points once, whole, in a What's new popup that scrolls. Only the newest
release's points: a player who skipped versions finds the others under What's new in the website's menu, which reads
the same file. So write each Added point for players, as `- **Short title** (#issue): text`, and add
`for contributors` in the brackets, like `(#272, for contributors)`, for points players don't need: those are left out
of both. A release is built before the workflow renames its Unreleased section, so the mod reads Unreleased as
its own version when there is no section for it.

Only a commit on the default branch can be released, and an existing tag must be on the commit the run builds, so tag
a merged commit on `master`. The **build** job makes the DLL with a read-only token, on every push and pull request.
Only the **release** job can write to the repository: it packs that DLL with `README.md`, `Icon.png`, `CHANGELOG.md`
and `LICENSE` from the same tagged commit, and pushes the rotated `CHANGELOG.md` from a worktree of the default branch.
One release runs at a time. Without a `TCLI_AUTH_TOKEN` secret the package isn't published to Thunderstore; the run
warns, and the package is in its artifacts to upload by hand.

Mod Helper wrote the first `build.yml`, but `GenerateActionsWorkflow` is `false` in the csproj, so it no longer writes
it again and changes to it are kept. Everything it downloads is pinned, so a release can be built again the same way:

- **MelonLoader and Mod Helper**: the minimum versions in `thunderstore.toml` (`[package.dependencies]`), so the DLL
  is built against what it tells players it needs. Mod Helper's `btd6.targets` comes from the same tag.
- **The game's assemblies**: the commit of `doombubbles/btd6-ci-dependencies` in `CI_DEPENDENCIES_REF`.
- **Actions**: third-party actions are pinned to a commit, with the version in a comment (`@<sha> # v1.13`); GitHub's
  own (`actions/*`, `github/*`) use version tags. Dependabot updates both, the pins included.
- **The .NET SDK**: `global.json` asks for SDK 10.0.100 or a newer 10.0 (`rollForward: latestFeature`), so a local build
  and CI's use the same SDK line.

The release job never puts the tag or the description into a script with `${{ }}`; scripts read them from `env`. It
makes the GitHub release before publishing to Thunderstore, and fails if it can't push the rotated `CHANGELOG.md`.

The job summary and the end of the release notes say which versions were used.

After a game update, set `CI_DEPENDENCIES_REF` in `build.yml` to the commit of `btd6-ci-dependencies` for the new
game version (its message says it, e.g. "Update for v57.2"). When the mod starts to need a newer MelonLoader or Mod
Helper, raise the minimum in `thunderstore.toml`; the build follows it.

Some differences between what is tested and what is released are on purpose:

- **The test report comes from a Debug build.** The released DLL is a Release build, merged with ILRepack. Only Debug
  builds know which code they were built from (`sourceHash`) and carry the website's data for `WebDataTest`, so the
  in-game tests run on Debug. The tests themselves are in both builds; the C# is the same.
- **`Optimize` is `False` in both builds.** It came with Mod Helper's template. It keeps the Release DLL's IL like the
  Debug DLL the tests ran on, and the JIT from inlining small methods, which Harmony couldn't patch. Turning it on
  would make the released mod differ from the tested one, for little gain.
- **Two game versions.** The game version in `TestResults/ingame.json` (the game the tests ran on) can be newer than the
  one CI builds against (`CI_DEPENDENCIES_REF`), since `btd6-ci-dependencies` is updated some time after the game.
  A build against the older assemblies that passes is fine; one that fails means the mod uses something new.
- **No analyzers.** There are no analyzers and no `TreatWarningsAsErrors`. The C# compiles without warnings, so keep
  it that way, but the game's assemblies change with every update, and a new warning shouldn't block a release.

`.github/workflows/codeql.yml` scans the C#, TypeScript and workflows with CodeQL on pushes to `master`, pull
requests and once a week. It builds nothing (`build-mode: none`), since the mod can't be built without the game.
Findings show up under the repository's **Security** tab.

### Dependency updates

Dependabot (`.github/dependabot.yml`) opens update PRs every week for the website's npm packages, the NuGet packages
of `Shared/`, `UnitTests/` and `PropertyTests/`, and the GitHub Actions. Minor and patch updates come as one PR per
ecosystem, major updates one by one. The mod itself has no NuGet packages to update; it uses the game's and
MelonLoader's assemblies.

- Merge an update PR when its checks pass. They don't run the in-game tests, so after an update that could reach the
  game (none of these do today), run those too.
- A major update can need code changes: fix them on the PR's branch, or close it with a note and add an issue.
- `build.yml` is included. Its MelonLoader, Mod Helper and game assemblies aren't actions, so they are bumped by hand
  (see **Releases** above).

## Updating for a new BTD6 version

`.github/workflows/game-version.yml` runs every day (and by hand) and opens an issue with the label `game-update` when
the game changes, so an update is noticed the same day:

- **A new version.** When Steam's news for the game names an update newer than `WorksOnVersion` in
  `ModHelperData.cs` (Ninja Kiwi posts one for every major update, like "Update 57.0!"), it opens "BTD6 58.0 is out".
- **A new build.** Hotfixes (57.1, 57.2, ...) get no news post, so it also watches the build id of Steam's public
  branch (from [steamcmd.net](https://www.steamcmd.net/)). A new build opens "New BTD6 build on Steam (…)": check the
  version on the title screen, and close the issue if nothing changed. A new build while an update's issue is still
  open is added to that issue, and a build issue becomes the version's issue when the news post comes a day later.

The issues keep what was seen in hidden markers, so a version or build never opens a second issue, also after it was
closed. The very first run opens and closes one issue for the build that was live then, which later ones are
compared with. The script is `tools/game-version/check.mjs`; `node tools/game-version/check.mjs --dry-run` shows
what it sees. Its tests are `node --test "tools/game-version/*.test.mjs"`. The workflow can only write issues.

The issue lists the steps below as tasks; the script reads them from this list, so keep it a numbered list:

1. Update the game, start it with the mod and look in `MelonLoader/Latest.log` for `[CustomBossChallenge]` lines from
   `PatchCheck`: which patches are missing?
2. If the Boss Creator button says a part is missing, find the renamed or moved method and fix the patch.
3. Run the unit tests and the in-game tests (see [In-game tests](#in-game-tests)).
4. Set `WorksOnVersion` in `ModHelperData.cs` to the new version (`VersionTest` checks that it matches the game).
5. Check that an unfinished `Continue.json` from the old version still continues, or is put aside with a message (#13).
6. When `doombubbles/btd6-ci-dependencies` has the new version, set `CI_DEPENDENCIES_REF` in `build.yml` (see
   [Releases](#releases)).
7. Add a changelog entry under **Fixed**, then make a patch release (x.y.**z**).

## Website

`web/` is a small website (Vite + TypeScript, no framework) that reads share codes without the game, shows the setup
like the Boss Creator does (Tier Preview, skulls, rules) and lists example codes. It has five pages: `index.html`,
`compare.html` (two setups side by side), `past-events.html` (the past boss events, #213), `stats.html` (their stats, #265) and `studio.html`, the Studio (#12, #79), which makes and changes setups with
the Boss Creator's controls (`web/src/studio/`), Advanced Mode's bosses per tier included (`tiers.ts`, #95), the
Challenge Editor's rules (`rules.ts`, #97) and its tower restrictions (`towers.ts`, #128), held to `ChallengeLimits`
with the same clamping the code reader uses. It is laid out like the Boss Creator (#133): rows with our own icons
(`icons.ts`), the boss buttons (`bossPicker.ts`), and the preview's Tier Preview and Skull Preview among the controls. It needs [Node.js](https://nodejs.org/) LTS:

```
cd web
npm install
npm run dev
```

Then open http://localhost:5173. To try the site on a phone, `npm run dev:lan` serves it on your local network too,
and prints the address to open on the phone (on the same network). `npm test` runs its tests and `npm run build`
puts the finished site in `web/dist`.

The Past Events page (`past-events.html`, #213) and the Stats page (`stats.html`, #265, numbers from `web/src/stats/compute.ts`) load `boss-events.json`, which isn't committed: run
`npm run boss-events` once in `web/` to build it into `web/public/` from `data/boss-events/`, as `pages.yml` does
before every deploy. The tests don't need it; they read the archive itself. The website's mapping
(`web/packages/share-code/src/pastEvents.ts`) is a port of the mod's `Config/PastEventRules.cs`, and
`web/test/past-event-cases.json` keeps the two the same: after changing the mod's mapping, run
`CBC_PAST_EVENT_CASES=1 dotnet test --project UnitTests` to write it again, then `npm test`.
`.github/workflows/pages.yml` does the same on GitHub and publishes the site to
https://pedersebastian.github.io/CustomBossChallenge/ whenever `web/` changes on master (or when run by hand).
Visits are counted with [GoatCounter](https://pedersebastian.goatcounter.com/) (the script at the end of
`web/index.html`): no cookies, only the path is sent, never a `#code=…`, and localhost isn't counted.

The website must read codes exactly like the mod, so the code reading and writing is a port of the mod's C# in its own
package, [`@cbc/share-code`](web/packages/share-code/README.md) in `web/packages/share-code` (#98), an npm workspace
the website imports and other tools can use too: `SetupCode` reading (`src/decode.ts`) and writing (`src/encode.ts`,
the same JSON as the mod; the deflated bytes may differ), `BossOptions.Sanitized` (`src/options.ts`), and
`ChallengeLimits`, `TierMath`, `SkullMath` and `TierBossMath` (`src/math/`). Its `src/data.json` is a copy of the part
of `game.json` codes need: after `WebDataTest` writes new game data, run `npm run sync-data` in `web/`
(`web/test/share-code-data.test.ts` fails until then). The website itself ports the Tier Preview numbers
(`web/src/preview/compute.ts`, which also has `normalGame`, the setup the strength chart compares with). The
timeline under the Tier Preview is `web/src/preview/timeline.ts`; its event rounds follow `BossRoundsMath.EventRounds`.
Change them together with the C#. Besides the fixtures below, `web/test/generated.test.ts` reads the random codes from
the property tests (see *Property tests*).

What only the game knows (the default challenge codes are made against, boss health, speed and skulls, map and tower
names) comes from the game, through the in-game test `WebDataTest`, into `web/src/data/`:

- `game.json`: the game data. The player's name and the random seed of the default challenge are left out.
  `mapDifficulties` has each map's group in the game (Beginner to Expert), which the Studio's map list is grouped by;
  a map without one goes under Other, and a map the data doesn't have yet is kept as it is in the code.
  `towerSets` has each tower's class (Hero, Primary, Military, Magic, Support) and `paragonTowers` the towers with a
  paragon, which the Studio's tower list uses.
- `tierlook.json`: the colours of tiers 6-10 per boss and how strong and fast their glow pulses, from
  `Config/TierLook.cs`, so the tier cards on the website glow like the boss does in the game
  (`web/src/preview/tierLook.ts`).
- `examples.json`: the example codes on the website, made with `SetupCode.Encode` from `Creator/ExampleSetups.cs`,
  the same list the Boss Creator shows, so they always load in the game.
- `fixtures.json`: codes with what the mod reads from them; the website's tests must read them the same way.

`game.json` also holds the game's limits, e.g. `limits.paragons`, how many paragons there are, so a Max Paragons of
that many or more shows as Unlimited.

Some cases are shared by the website's tests and the unit tests, in `web/test/`, so both sides read them alike:
`link-cases.json` (the code in a pasted link, %-escapes included), `skull-cases.json` (custom skulls, rounded like
.NET), `tier-boss-cases.json` (`TierBossMath.With`, `Step` and `Resolve`, which the Studio's Advanced Mode uses, #95),
`option-cases.json` (a code's boss options of every JSON type, made with the mod's own `CodeFormat` and
Json.NET), `paragon-cases.json` (the Max Paragons slider), `random-cases.json` (Random's weights, and the bosses per
tier it makes from listed random numbers, so the Studio's Random and the Boss Creator's give the same values) and
`code-strictness.json` (hand-made and damaged codes: strict JSON, Base64 and deflate, and text in
options trimmed and compared like C#'s `Trim` and `OrdinalIgnoreCase`, #174). When the mod reads one of them differently, change both sides and the file. `website-codes.json` goes the
other way: codes the Studio made with its own controls, which `UnitTests/CodeFormatTests.cs` reads with the mod's
`CodeFormat`, so codes made on the website load in the mod unchanged. After changing the Studio or the encoder, write
it again with `$env:CBC_WEBSITE_CODES = "1"; npm test; Remove-Item env:CBC_WEBSITE_CODES` in `web/`. `web/test/dom.test.ts` runs
in [happy-dom](https://github.com/capricorn86/happy-dom) and covers what needs a page: the copy buttons, what screen
readers are told and links within the page. `web/test/pages.test.ts` does the same for the code viewer, Compare and the
examples: links in the address bar, Back, the skip link and an address bar that can't be changed (#173).

`WebDataTest` checks that these files still match the game and the mod. Only Debug builds carry them, so a Release
build skips the check. After a game update or a change to the code
format, Tier Preview, the tier look or the examples, write them again by running the in-game tests with the
environment variable `CBC_WEB_DATA` set to the folder (start the game with PowerShell `Start-Process` so it gets the
variable), then rebuild the mod and run the tests again:

```
$env:CBC_WEB_DATA = "<repo>\web\src\data"
```

The names of maps, towers, modes and difficulties in `game.json` are the game's own texts, and the website is English,
so writing the files needs the game in English (#218). In another language `WebDataTest` refuses to write them, and
when it checks them it leaves those names out.

The bosses' portraits (#206) are the one piece of the game's art on the website: `web/public/bosses/`, credited to
Ninja Kiwi in every page's footer (`web/src/preview/portrait.ts` shows them, and the boss's first letter if one doesn't
load). They come from the game through the in-game test `BossPortraitsTest`, which otherwise checks that every
portrait still loads: run it windowed with `CBC_TESTS=BossPortraitsTest` and `CBC_PORTRAITS=<a scratch folder>`, then
`python -I web/scripts/portraits.py <that folder> web/public/bosses` (needs Pillow). The folder's README has the
details; `web/test/boss-portraits.test.ts` fails while a boss has no portraits.

A shared link to the website shows a card with `web/public/og-card.png` (1200 × 630), the tags in `web/index.html`
and the address in `web/.env` (`VITE_SITE_URL`, which link previews need in full; change it if the site moves). A
`#code=…` never reaches the server, so every link shows the same card. The picture is made from
`web/scripts/og-card.html` with Chrome; the command is at the top of that file. Keep it under ~100 KB, e.g. by saving it
as a palette PNG.

## Boss events archive

The mod carries the whole archive: `CustomBossChallenge.csproj` runs `node tools/boss-events/archive.mjs --bundle` into
`obj/` and builds the gzipped `boss-events.json` in (#146), so building the mod needs Node 24 (a Release build fails
without it, a Debug build only warns). It is made again only when a file in `data/boss-events/` or the archiver
changes. Being in `obj/`, it isn't part of the source hash, so the archiver's daily commits don't need a new in-game
test run before a release. At the game's start the mod downloads the published `boss-events.json` in the background
(`Persistence/PastEvents.cs`), unless `--modhelper.offline` is set (the headless tests) or the setting is off.

`data/boss-events/` holds every official Boss Bloon Event, one file per event, for the Past Events list (#143). The
format, the sources and their licences are in [data/boss-events/README.md](data/boss-events/README.md).

New events are saved every day by the **Boss events** workflow (`.github/workflows/boss-events.yml`), which commits
them to master as the Actions bot and then publishes `boss-events.json` with the website (it calls `pages.yml`, since
its own commits don't start other workflows). It can also be run by hand from the Actions tab, e.g. to publish again.
The script it runs works locally too (Node 24, no packages):

```
node tools/boss-events/archive.mjs --dry-run
node tools/boss-events/archive.mjs
node tools/boss-events/archive.mjs --bundle web/public/boss-events.json
```

The first prints the events the archive doesn't have yet, the second saves them, and the third builds
`boss-events.json` from the files without going online (`web/public/boss-events.json` isn't committed).

The events from before the archiver were added once with `tools/boss-events/backfill.mjs` (Node 24, no packages):

```
node tools/boss-events/backfill.mjs --dry-run
node tools/boss-events/backfill.mjs --jxu-commit bf88fabd02e01343e96812a6e7285fb3abca7ffb
```

It downloads Blooncyclopedia's event history pages and [jxu/btd6-events](https://github.com/jxu/btd6-events) (at
the given commit, or its newest) into `tools/boss-events/.cache/` (not committed; `--refresh` downloads again), picks
the best source for every event, and writes the files. Running it again changes nothing. It never changes a file the
archiver saved from the API, and only replaces a file with a better source. What it skips or guesses is printed at the
end. The tests (`node --test "tools/boss-events/*.test.mjs"`) run on the samples in `tools/boss-events/fixtures/`:
they check the wiki's rules against Ninja Kiwi's for the same events, and that the archiver adds only new events,
never touches a file it has, and skips bad answers.

## Translations

The mod's texts are in `Localization/`, one file per language that BTD6 supports, e.g. `Localization/German.json`.
The game shows the file for its own language, and English where a text is missing. The translations were
machine-made, so corrections are welcome. The easiest way is the
[Translation fix](https://github.com/pedersebastian/CustomBossChallenge/issues/new?template=translation.yml) issue
form; to change a file yourself:

1. Open the language's file on GitHub and press the pencil (**Edit this file**). GitHub makes a copy for you and
   turns your change into a pull request.
2. Change only the text after the colon. Each line looks like this:

   ```json
   "CustomBossChallenge-SkullPreview": "Totenkopfvorschau",
   ```

   - Leave the key before the colon (`CustomBossChallenge-SkullPreview`) exactly as it is, and don't add, remove or
     move lines: every file has the same keys in the same order as `English.json`.
   - Keep placeholders like `{0}`. The game puts a number or name there, e.g. `{0} tiers` becomes `7 tiers`.
   - Keep the quotes and the comma at the end of the line. Use `\"` for a quote inside a text.
   - Keep the game's own words where it has them, e.g. its names for Elite, tiers and the Challenge Editor.
   - In Chinese, Japanese and Korean, the game's fonts only have the characters the game itself uses: another one
     shows as a box. `LanguageLayoutTest` names any character a translation needs that the fonts lack (#244).
3. Describe what you changed and propose the change. The **Translations** check above runs on the pull request and
   says if a key, placeholder or comma went missing.

New texts are added to `Menus/Texts.cs` (with the English text) and to every file in `Localization/`, at the same
place. `LocalizationTest` and `Check-Localization.ps1` check that all files have them. The translations are built
into the DLL, so build the mod to see a change in the game.

`Localization/english-sources.txt` records, for every key and language, a short hash of the English text the
translation was made from, so changing an English text without the others fails the **Translations** check. After
translating new or changed English texts, record them with

```
powershell -ExecutionPolicy Bypass -File .github/scripts/Check-Localization.ps1 -UpdateSources -Language German,French
```

(all languages without `-Language`). A fix to a translation alone, with English unchanged, needs nothing here.

### Pseudo language

To see whether a new or longer text still fits before anyone translates it, run `LanguageLayoutTest` with the made-up
pseudo language (#267): start the game with `CBC_TESTS=LanguageLayoutTest` and `CBC_LANGUAGES=Pseudo` (add
`CBC_SCREENSHOTS=<folder>` and leave out `-batchmode` for pictures). The game stays in English, but every text of the
mod is about 40 % longer, accented and in brackets, made from `English.json` by `Config/PseudoLocalization.cs`, so
`Speed per Tier` shows as `[Śpééd pér Tíér ~~~]`. The test then reports texts that are cut off, wrap, overflow or run
into each other, and English words that are neither in a bracket nor one of the game's own texts: those never went
through `Localization`. `CBC_LANGUAGES=German,Pseudo` checks both. It isn't part of the normal run, since its texts
are longer than any real translation needs to fit.
