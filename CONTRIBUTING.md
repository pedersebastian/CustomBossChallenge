# Development

Technical notes for building and testing Custom Boss Challenge. For what the mod does and how to install it, see the
[README](https://github.com/pedersebastian/CustomBossChallenge/blob/master/README.md).

## Building from source

1. Install the .NET SDK, MelonLoader and BTD6 Mod Helper (with the game run at least once so Mod Helper can set up
   its references).
2. Clone this repository into your BTD6 mod sources folder.
3. Build `CustomBossChallenge.sln` (for example `dotnet build -c Release`). The built DLL is copied to the game's
   `Mods` folder automatically.

`Icon.png` is generated by `tools/GenerateIcon.ps1`
(`powershell -ExecutionPolicy Bypass -File tools/GenerateIcon.ps1`).

### The tier glow shader

Tiers above 5 glow with a shader of the mod's own, `UnityProject/Assets/TierGlow/TierGlow.shader`. The game can only
load shaders built with its own Unity version, so it is built into `Bundles/tierlook.bundle`, which is committed and
built into the DLL; the checks on GitHub don't build it, since that needs a Unity license. Only rebuild it after
changing the shader, or when a BTD6 update moves to another Unity version (MelonLoader logs it as `Unity Version`, and
the game's URP version is in `BloonsTD6_Data/resources.assets`, e.g. `render-pipelines.universal@17.3.0`):

1. Install that Unity version (the same major and minor version, e.g. 6000.3, with the latest patch is enough) with
   Unity Hub and activate a Personal license. No modules are needed.
2. Build the bundle:

   ```
   "C:\Program Files\Unity\Hub\Editor\<version>\Editor\Unity.exe" -batchmode -quit -nographics -projectPath UnityProject -executeMethod BuildTierLook.Build -logFile -
   ```

   It compiles the shader for Direct3D 11, Direct3D 12 and Vulkan and writes `Bundles/tierlook.bundle`.
3. Run `TierLookTest` (`CBC_TESTS=TierLookTest`): it fails if the game can't use the shader. Without the bundle, or
   when the game can't run it, players still get a simpler glow made from the game's own shaders.

The look itself (colours per boss, strength per tier) is in `Config/TierLook.cs`. `TierLookTour` saves tiers 5-10 of
every boss next to each other when the game is started with `CBC_SCREENSHOTS=<folder>` (`CBC_TIERLOOK_BOSSES=Lych,Vortex`
picks bosses).

## Running the tests

### Unit tests

The logic that doesn't need the game (tier, spawn round and skull math, the keyboard shortcut rules, the share code
format and writing the mod's files) has xUnit tests in `UnitTests/`. Those source files are built on their own in
`Shared/`, so the tests build and run in seconds without BTD6:

```
dotnet test --project UnitTests
```

Keep the files in `Shared/` free of the game's types (`Il2Cpp...`, `BTD_Mod_Helper`), or the project won't build.

### Property tests

Share codes are also tested with random data, in F# with [FsCheck](https://fscheck.github.io/FsCheck/), in
`PropertyTests/`. Thousands of random setups the Boss Creator can make, and broken codes, check that:

- a code reads back as exactly the setup it was made from, and encoding that setup again gives the same code;
- codes use `CBC2:` only when they need it, and only characters chat apps leave alone;
- broken codes (cut short, changed, junk, too big once unpacked) are refused as `Invalid` or `TooNew` and never throw.

```
dotnet test --project PropertyTests
```

The tests run `Persistence/CodeFormat.cs` (the text format, without the game), against the defaults in
`web/src/data/game.json`. When a property fails, FsCheck shrinks it to the few values that matter and prints them as
the JSON the code holds; add that case to `SetupCodeTest` or `WebDataTest`'s fixtures, then fix it.

They also check `web/test/generated-codes.json`: 200 random codes and 50 or so broken ones from a fixed seed, which
the website's tests must read exactly like the mod. After changing the generators or the code format, write it again:

```
$env:CBC_GENERATED_CODES = "1"; dotnet test --project PropertyTests; Remove-Item env:CBC_GENERATED_CODES
```

### In-game tests

Everything else runs inside the game, with automated tests built on Mod Helper's `ModTest`. They cover:

- preparing the editor's challenge for a boss game
- the Random button: a thousand random setups that must all be playable, spread like the game's own randomizer
- extra tier models for every boss and Elite tier, Speed and Health per Tier for every tier of every boss, and real
  games played to victory with 6 and with 2 tiers
- a vanilla and a custom Bloonarius game compared side by side (speed, health, skulls, cash, unranked)
- the ranked and co-op guards, and that every record, boss progress and badge method is still guarded after a
  game update
- restarting a custom game, and losing one to a boss that isn't defeated
- the Max Paragons limit, enforced by the game in a custom game with a real paragon placed
- saving and loading the last setup, including broken files and values out of range
- share codes: the round trip, short codes, and broken, damaged or too new codes that must never load
- hand made, malicious codes: type names, extreme values, rich text in the name, and codes that unpack to too much
  or nest too deeply
- the main menu button, and the whole Boss Creator flow in the real Challenge Editor, from editing the boss options
  to copying and pasting share codes and pressing Play, including that the normal Challenge Editor and your own
  draft stay untouched and that Play refuses unsupported modes and missing bosses
- the keyboard (`KeyboardTest`): the Ctrl shortcuts, Tab, the arrows, Enter and Space through the Boss section's
  controls (`BossEditorSection.FocusStops`, which controller support can use too), Esc in a field cancelling only the
  edit, and nothing of it in the normal Challenge Editor. Real key presses can't be faked, so the test hands the key
  press to `BossCreatorKeys.Handle`
- the layout on 16:9, 16:10, 4:3, 21:9 and 32:9 (`LayoutTest`): the Boss Creator button and Play overlap nothing,
  stay on the screen, Play stays behind the editor's own panels, and every control of the Boss section stays inside
  it. The game can change its resolution even with `-batchmode`, so this runs with the other tests

Run them from Visual Studio / Rider with the **BloonsTD6 (Tests)** launch profile, or from the game folder:

```
BloonsTD6.exe moddingDev -batchmode --modhelper.offline --modhelper.only='CustomBossChallenge;' --modhelper.noaudio --modhelper.run -q test mod CustomBossChallenge
```

The result is written to `MelonLoader/Latest.log`, e.g. `Ran 25 test(s), 25 succeeded, 0 failed`.

The screenshots in the README come from the `ScreenshotTour` test. It only runs in a windowed game (without
`-batchmode`) started with the environment variable `CBC_SCREENSHOTS=<folder>`. To look at other screen formats, also
set `CBC_RESOLUTIONS`, e.g. `1280x800,1024x768,1680x720,1920x540`: the tour is then taken once per size, each in a
subfolder of `<folder>` named after the size.

### Compatibility with other mods

Players run this mod next to others, so it is tested with the most downloaded mods and the ones that touch bosses,
the Challenge Editor, rounds, the main menu or saves (listed in `.github/scripts/compat-candidates.json`). The results
are in [issue #24](https://github.com/pedersebastian/CustomBossChallenge/issues/24). Run this again after a BTD6 update
or when a mod in the list changes a lot. The other mods are third-party code: they are downloaded into a folder outside the repo and only run
inside the game.

```
# 1. Download the latest release of every listed mod (prints name, size and SHA-256)
powershell -ExecutionPolicy Bypass -File .github/scripts/Get-CompatMods.ps1 -Out C:\cbc-compat\mods

# 2. Which methods both mods patch, without the game
dotnet fsi .github/scripts/Scan-Patches.fsx "<game>\Mods\CustomBossChallenge.dll" C:\cbc-compat\mods C:\cbc-compat\scan.md

# 3. All in-game tests with this mod alone, then with each other mod (A, B, all, a name, or names joined by +)
powershell -ExecutionPolicy Bypass -File .github/scripts/Test-ModCompatibility.ps1 -ModsFolder C:\cbc-compat\mods -Results C:\cbc-compat\runs -Mods none,A,B

# 4. Screenshots with each mod, compared with two runs of this mod alone (the second one measures animation noise)
powershell -ExecutionPolicy Bypass -File .github/scripts/Test-ModCompatibility.ps1 -ModsFolder C:\cbc-compat\mods -Results C:\cbc-compat\runs -Mods none,none -Screenshots
powershell -ExecutionPolicy Bypass -File .github/scripts/Compare-Screenshots.ps1 -Baseline C:\cbc-compat\runs\screenshots\none -Candidates <second baseline>,<mod folders> -FirstIsNoise -Out C:\cbc-compat\report
```

`Test-ModCompatibility.ps1` copies each mod into the game's `Mods` folder for one run and removes it afterwards,
stops if the folder isn't as it was, copies the game profile to `<Results>\profile-backup` before the first run, and
reruns failing tests once so that a flaky test isn't blamed on another mod. Each run adds a line to
`<Results>\results.jsonl`, and its `Latest.log` is kept in `<Results>\logs`.

`ModConflictTest` writes every other mod's patch on a method this mod patches to the log as a `CBC-CONFLICT|` line.
`HarmonyBehaviourTest` checks what another mod's prefix can do to ours: in MelonLoader's Harmony every prefix and
postfix still runs when one of them skips the method, so another mod can't switch a guard off that way, only change a
value before or after us. Outside of tests, the mod logs a warning at startup when another mod patches one of the
guards (`[GuardPatch]`), so a bug report's `Latest.log` shows it.

## Checks on GitHub

`.github/workflows/checks.yml` runs on every push and pull request, without the game:

- **Translations**: every `Localization/*.json` must be valid JSON without duplicate keys, have exactly the keys of
  `English.json` in the same order, keep its `{0}` placeholders and leave no text empty, and every text in
  `Menus/Texts.cs` must exist in English.
- **Release version** (tags only): the tag must match `Version` in `ModHelperData.cs`, which Mod Helper uses to tell
  players about updates, and `CHANGELOG.md` must have notes for it. This runs next to the release in `build.yml`, so
  it marks a bad release instead of stopping it: run it before tagging.
- **Unit tests**: `dotnet test --project UnitTests`, see above. The in-game tests can't run on GitHub and still have
  to be run locally.
- **Property tests**: `dotnet test --project PropertyTests`, see above.
- **Website**: `npm test` and `npm run build` in `web/`, see below.

The first two are PowerShell scripts that also run locally in Windows PowerShell:

```
powershell -ExecutionPolicy Bypass -File .github/scripts/Check-Localization.ps1
powershell -ExecutionPolicy Bypass -File .github/scripts/Check-Release.ps1 -Tag 2.3.0
```

`build.yml` is generated by Mod Helper and overwritten when the mod is built, so other checks belong in
`checks.yml`.

`.github/workflows/codeql.yml` scans the C#, TypeScript and workflows with CodeQL on pushes to `master`, pull
requests and once a week. It builds nothing (`build-mode: none`), since the mod can't be built without the game.
Findings show up under the repository's **Security** tab.

### Dependency updates

Dependabot (`.github/dependabot.yml`) opens update PRs every week for the website's npm packages, the NuGet packages
of `Shared/`, `UnitTests/` and `PropertyTests/`, and the GitHub Actions. Minor and patch updates come as one PR per
ecosystem, major updates one by one. The mod itself has no NuGet packages to update; it uses the game's and
MelonLoader's assemblies.

- Merge an update PR when its checks pass. They don't run the in-game tests, so after an update that could reach the
  game (none of these do today), run those too.
- A major update can need code changes: fix them on the PR's branch, or close it with a note and add an issue.
- `build.yml` is left out, since Mod Helper writes it again; its actions are updated with Mod Helper's template.

## Website

`web/` is a small website (Vite + TypeScript, no framework) that reads share codes without the game, shows the setup
like the Boss Creator does (Tier Preview, skulls, rules) and lists example codes. It needs [Node.js](https://nodejs.org/)
LTS:

```
cd web
npm install
npm run dev
```

Then open http://localhost:5173. `npm test` runs its tests and `npm run build` puts the finished site in `web/dist`.
`.github/workflows/pages.yml` does the same on GitHub and publishes the site to
https://pedersebastian.github.io/CustomBossChallenge/ whenever `web/` changes on master (or when run by hand).
Visits are counted with [GoatCounter](https://pedersebastian.goatcounter.com/) (the script at the end of
`web/index.html`): no cookies, only the path is sent, never a `#code=…`, and localhost isn't counted.

The website must read codes exactly like the mod, so parts of the mod are ported to TypeScript: `SetupCode` reading
(`web/src/code/decode.ts`), `BossOptions.Sanitized` (`options.ts`), `TierMath` and `SkullMath` (`web/src/math/`) and
the Tier Preview numbers (`web/src/preview/compute.ts`). Change them together with the C#. Besides the fixtures below,
`web/test/generated.test.ts` reads the random codes from the property tests (see *Property tests*).

What only the game knows (the default challenge codes are made against, boss health, speed and skulls, map and tower
names) comes from the game, through the in-game test `WebDataTest`, into `web/src/data/`:

- `game.json`: the game data. The player's name and the random seed of the default challenge are left out.
- `examples.json`: the example codes on the website, made with `SetupCode.Encode` from `Creator/ExampleSetups.cs`,
  the same list the Boss Creator shows, so they always load in the game.
- `fixtures.json`: codes with what the mod reads from them; the website's tests must read them the same way.

`WebDataTest` checks that these files still match the game and the mod. After a game update or a change to the code
format, Tier Preview or the examples, write them again by running the in-game tests with the environment variable
`CBC_WEB_DATA` set to the folder (start the game with PowerShell `Start-Process` so it gets the variable), then rebuild
the mod and run the tests again:

```
$env:CBC_WEB_DATA = "<repo>\web\src\data"
```

A shared link to the website shows a card with `web/public/og-card.png` (1200 × 630), the tags in `web/index.html`
and the address in `web/.env` (`VITE_SITE_URL`, which link previews need in full; change it if the site moves). A
`#code=…` never reaches the server, so every link shows the same card. The picture is made from
`web/scripts/og-card.html` with Chrome; the command is at the top of that file. Keep it under ~100 KB, e.g. by saving it
as a palette PNG.

## Translations

The mod's texts are in `Localization/`, one file per language that BTD6 supports, e.g. `Localization/German.json`.
The game shows the file for its own language, and English where a text is missing. The translations were
machine-made, so corrections are welcome. The easiest way is the
[Translation fix](https://github.com/pedersebastian/CustomBossChallenge/issues/new?template=translation.yml) issue
form; to change a file yourself:

1. Open the language's file on GitHub and press the pencil (**Edit this file**). GitHub makes a copy for you and
   turns your change into a pull request.
2. Change only the text after the colon. Each line looks like this:

   ```json
   "CustomBossChallenge-SkullPreview": "Totenkopfvorschau",
   ```

   - Leave the key before the colon (`CustomBossChallenge-SkullPreview`) exactly as it is, and don't add, remove or
     move lines: every file has the same keys in the same order as `English.json`.
   - Keep placeholders like `{0}`. The game puts a number or name there, e.g. `{0} tiers` becomes `7 tiers`.
   - Keep the quotes and the comma at the end of the line. Use `\"` for a quote inside a text.
   - Keep the game's own words where it has them, e.g. its names for Elite, tiers and the Challenge Editor.
3. Describe what you changed and propose the change. The **Translations** check below runs on the pull request and
   says if a key, placeholder or comma went missing.

New texts are added to `Menus/Texts.cs` (with the English text) and to every file in `Localization/`, at the same
place. `LocalizationTest` and `Check-Localization.ps1` check that all files have them. The translations are built
into the DLL, so build the mod to see a change in the game.
